# AGENTS.md

This file provides guidance to coding assistant agents when working with code in this repository.

## Commands

```sh
make test       # run the ERT suite
make compile    # byte-compile arche-diary.el — must finish with no warnings
make clean      # remove *.elc
```

The Makefile expects denote and org under `~/.emacs.d/straight/build/{denote,org}`. Override with `DENOTE_DIR=...` / `ORG_DIR=...` / `EMACS=...` if needed.

By default Emacs loads a stale `arche-diary.elc` in preference to the source (it only warns "using older file"), so edits can appear to pass. `make test` and the command below set `load-prefer-newer` to rule that out; any other batch run that loads the package needs the same.

Run a single test:

```sh
emacs -Q --batch --eval '(setq load-prefer-newer t)' -L . -L test \
  -L ~/.emacs.d/straight/build/denote \
  -L ~/.emacs.d/straight/build/org \
  -l test/arche-diary-tests.el \
  --eval "(ert-run-tests-batch-and-exit '\"parse-month-offsets\")"
```

The selector is a regexp matched against test names (all named `arche-diary-tests/...`).

## Architecture

Single-file package: all production code lives in `arche-diary.el`, organized top-to-bottom as: customs → time helpers → parsing → file/backend helpers → buffer/heading helpers → image helpers → public commands → HTML export. Tests are in `test/arche-diary-tests.el` and use a fixture macro (`arche-diary-tests--with-dir`) that rebinds the customs dynamically to a fresh `make-temp-file` directory and cleans up buffers + dir after each test.

Cross-cutting concerns when editing:

**Backend switch.** `arche-diary-file-creation-system` is `'denote` or `'plain`. Both backends are reached through `arche-diary--month-file` (lookup) and `arche-diary--ensure-monthly-file` (lookup-or-create), which `pcase` on the backend. `arche-diary--find-or-list-month-files` is the canonical listing — it returns `(YEAR MONTH PATH)` triples sorted ascending and is what HTML export, nav, and `--latest-date-globally` consume. For denote, it filters by the *first* element of `arche-diary-denote-keywords` (the others are applied at creation but not used for filtering). The actual filesystem scan lives in `arche-diary--list-month-files` (for denote, `denote-directory-files` is ~0.3s/call regardless of file count); `--find-or-list-month-files` is a thin accessor that returns the per-export cache `arche-diary--month-files-cache` when one is bound, else scans. Always call the *accessor*, never `--list-month-files`, from any export-time path so the one scan is shared.

**Argument parsing.** `arche-diary--parse-month` and `arche-diary--parse-date` are the only entry points that accept user-facing arguments. They dispatch on type (nil → today/this-month, symbol, integer, cons/list, string) and the string branch has its own regex cascade. Adding a new accepted format means touching one of these dispatchers *and* the corresponding doc/README; the public commands just pass `month` / `date` straight through. `parse-date` takes `BUFFER-MONTH` to scope bare day strings (`"15"`) and `ALLOW-WEEKDAYS` to enable `'mon..'sun` (allowed in `visit-date` / `fill-dates`, rejected in `add-date`).

**Heading format and regex are paired.** `arche-diary-date-heading-format` controls how a heading is *written*; `arche-diary-date-heading-regexp` controls how every helper *reads* one. If you change the format, the regex's group-1 must still capture an ISO `YYYY-MM-DD`. The whole package — insertion logic, HTML export, fill-dates, latest-date — depends on this contract. Filename and title formats have a similar unstated contract: `--list-month-files` hard-codes `YYYY-MM.org` (plain) and `--YYYY-MM__` (denote), and `--current-buffer-month` hard-codes `#+title: YYYY-MM`, whatever `arche-diary-filename-format` / `arche-diary-title-format` say.

**HTML export does not use `org-html-export-to-html` for the whole file**, because date order and within-day note order must be reversed. Instead, `arche-diary--read-month-data` walks the Org file with regex matches against the date heading and collects level-2 notes per date in document order, then `arche-diary--month-section-html` reverses both lists and emits HTML. Each note's body is rendered through `arche-diary--org-string-to-html`, which is a thin wrapper around `org-export-string-as ... 'html t` (body-only). This means new Org syntax in notes is rendered correctly, but you must not assume the whole-file Org exporter ran — e.g., `#+OPTIONS` and other file-level keywords are ignored.

**Heading-level export exclusion is the package's own, because the regex walk runs before any exporter.** A date heading (level 1) or note heading (level 2) carrying a tag in `arche-diary-html-noexport-tags` (default `("noexport")`) is dropped — along with everything beneath it — by `arche-diary--heading-excluded-p` checks in `arche-diary--read-month-data` (dates) and `arche-diary--collect-notes-after-point` (notes); the same helpers strip trailing tags off the displayed title via `arche-diary--heading-strip-tags` so a tag never leaks into the page. Subheadings *inside* a note body (level 3+) are not handled here — they pass through `org-export-string-as`, which honors the same tag via Org's stock `org-export-exclude-tags`, so the default `"noexport"` works uniformly at every heading level even though two different mechanisms enforce it.

**Per-month links are a level-1 `Links` subtree (`arche-diary-links-heading`) parsed by regex, never the Org exporter.** It sits above the date headings; because it is not a date heading, every date-regexp scan ignores it, so it never renders as a body section and a new first date still appends at `point-max` after it. `--html-document` emits the links *below* the month `nav`, not inside `<header>`: month pages use their own month's links, `index.html` only the latest month's. `--seed-links` copies the most recent earlier month's subtree verbatim, only into a freshly created file. A nil heading disables parse, render and seed alike.

**Opening external links in a new tab is a single document-level rewrite, not per-link.** `--external-links-new-tab` runs over the whole assembled page as the last step of `--html-document`, covering the link list and note bodies in one place. Org's exporter has no switch for this, so don't do it per note; relative hrefs (page title, month nav, images) are deliberately skipped.

Before `arche-diary--org-string-to-html` exports, it runs `arche-diary--unfill-cjk` on the body, because an in-paragraph newline exports as a space, which is visibly wrong between CJK characters. It works on the *source*, since a post-HTML pass can't see across a tag (`…したら\n[[…]]`): a break is dropped when either adjacent char is CJK and otherwise becomes one space, so ordinary wrapped Latin text renders the same. A line ending in an Org hard break (`\\`) is never folded: Org only reads it as a break at the end of a line, so folding would export a literal `foo\\ bar` instead of `<br />`. Org only recognizes an emphasis marker next to whitespace or a line edge, so where a dropped break would press a marker against a CJK character (`…したら\n~Fuzzel~`) the separator is a zero-width space instead (`arche-diary--zero-width-space`, a raw, invisible character in the source that looks like `""`; don't retype it). Only continuation lines fold: blank lines, headings, bullets, tables, keywords, clock lines, planning lines directly under a heading, blocks and LaTeX environments stay on their own lines. The rules mirror Org's, which ignores case and only reads a planning keyword as planning right after a heading, so everywhere else such a line is ordinary text and folds; folding text onto a real planning line loses that text. `arche-diary-tests/unfill-does-not-change-non-cjk-rendering` compares output with unfill on and off, so add any new line-based syntax there.

`arche-diary-export-html` dispatches on its `MONTH` arg: an explicit month or `'all` force-renders, but **no arg is incremental** — it renders only months where `arche-diary--month-html-stale-p` is true (HTML missing, or source mtime strictly newer than the HTML), and is a true no-op (no `index.html` rebuild, no `arche-diary-after-export-hook`) when nothing is stale. Because this only compares source mtimes, a renderer, CSS or defcustom change reports "already up to date"; check those with `'all` or an explicit month. Re-rendering only stale months is safe because nav (`arche-diary--nav-html`, fed only the months *strictly before* the page's own month; `index.html` is fed every month) never links *forward*, so a newer or changed month never invalidates an older page's HTML; a brand-new month is caught as "HTML missing". `index.html` is the only cross-month artifact and derives from the same sources, so "rebuild index iff ≥1 month exported" is complete.

**Export is memoized for the dynamic extent of one command via `arche-diary--with-export-caches`, which wraps the whole `arche-diary-export-html` body** and binds a month-listing cache and a path→data cache (`--month-data` is the cache-aware front for `--read-month-data`). Both are sound only because Org sources are never modified during an export. Commands that scan outside an export see no binding and read fresh, which is correct. The macro also binds `org-modules-loaded` to t to avoid a multi-second module load on the first export; its docstring explains why that is safe. Image copies use the same staleness model: `arche-diary--image-copy-current-p` compares mtimes instead of reading image bytes on every export (size cannot join it — see metadata stripping below). That only works if each source has its own destination, so images outside `arche-diary-image-directory`, which have no subtree to mirror, get a hash of their path in the filename (`--hashed-image-name`); a bare basename would publish the first-copied image for every source of that name. `--files-identical-p` is still used at *insertion* time, where byte-exactness picks a non-colliding filename.

**Image handling spans insertion and export.** `arche-diary-insert-image` copies the source into `arche-diary-image-directory` (by default under a per-date subdirectory; `arche-diary-image-date-subdir`) and inserts a `#+CAPTION:` / `#+NAME: fig:...` / `#+ATTR_HTML:` block plus a `[[file:...]]` link (by default relative to `arche-diary-directory`; `arche-diary-image-link-type`). Because Org files live in `arche-diary-directory` but HTML goes to `arche-diary-html-directory`, one relative path can't resolve from both. The bridge is `arche-diary--rewrite-image-links-for-export`, called from `arche-diary--org-string-to-html`: it copies each image into the html dir and rewrites the link. If you add another export path, route image-bearing Org through that same helper.

A double prefix to `arche-diary-insert-image` makes a `#+begin_gallery` block. That contract is split between the inserter, Org's special-block export (`<div class="gallery">`) and the `.gallery` rule in `arche-diary-html-css`.

Always read `arche-diary-html-directory` and `arche-diary-image-directory` through the accessors `arche-diary--html-directory` / `arche-diary--image-directory`, never the customs directly, or the "set only `arche-diary-directory` and the rest follow" contract breaks.

**Image metadata (EXIF/GPS) is stripped at export, on the published copy — deliberately not at insertion.** The export copy is the *only* image that leaves the machine, and every image a note links to passes through `arche-diary--rewrite-image-links-for-export`, whether it is one of the diary's own copies under `images/`, an original linked in place by `insert-image`'s NO-COPY, or a hand-written `[[file:...]]` link. Stripping at insertion would instead have covered only images going forward *and* only the copied ones, leaving those three paths publishing EXIF — so the chokepoint is the export, and that is where `arche-diary--copy-image-for-export` (the copy step, replacing a bare `copy-file`) does it. The corollary is that `arche-diary-directory` keeps its metadata intact: the diary is a faithful archive, and only what is published is scrubbed. Don't "helpfully" move the strip upstream into `insert-image`. mtimes can't show whether a copy was stripped, so only a forced export writes a current image again, via `arche-diary--force-image-copy`. That is bound only around the renders of the requested months, not the index rebuild: `index.html` reads other months too, and forcing one month must not rewrite their images.

The mechanics are in `arche-diary--copy-image-for-export` (raster only: the strippers refuse or rasterize SVG). Never point a stripper at `src`: it only runs on a temp copy, because a file the user owns is only ever read. A missing or failing program degrades to an unchanged copy plus a message and must not fail an export, but it must not replace a copy that is still current: on a forced export that copy may be the stripped one, and the original would put the metadata back. The exiftool default keeps two display-only things: the ICC profile (`--icc_profile:all`), which holds nothing about the photo and whose loss dulls wide-gamut images, and the orientation tag (`-tagsfromfile @ -Orientation`), without which a photo rotated by tag publishes sideways. ImageMagick's `-strip` can't keep the tag, so those entries bake the rotation in with `-auto-orient`. Because these flags decide what is published, `arche-diary-tests/default-strip-command-keeps-only-orientation` runs the real exiftool when it is installed. Known limitation: on TIFF, exiftool cannot delete IFD0 (a minor warning, exit 0, so it counts as success), so make, model and similar tags survive there even though GPS goes. A stripped destination is no longer a byte copy, so `arche-diary--image-copy-current-p` compares **mtime only**; a size test would re-strip every image on every export. Tests stub the tool with `("sh" "-c" "printf STRIPPED > \"$0\"")` rather than requiring exiftool/ImageMagick.

**Buffer interactions are careful about leaks.** Read-only global scans use the `(or (get-file-buffer path) (find-file-noselect path))` pattern and only `kill-buffer` files they opened themselves (see `arche-diary--latest-date-globally`). `arche-diary-fill-dates` is the write-and-show counterpart: it snapshots the user's file buffers up front (`pre-buffers`), and `arche-diary-fill-dates-keep-buffers` governs what it kills afterwards. The snapshot, not a per-iteration `get-file-buffer` check, is what makes "did the user already own this?" reliable, because by day 2 of a month `get-file-buffer` returns the buffer we created on day 1.

## Conventions

Public symbols are `arche-diary-*`, internal helpers are `arche-diary--*` (double-dash), matching the user's other `arche-*` packages. Interactive commands carry `;;;###autoload`. The package follows the existing `arche-*` style from `~/arche/emacs/arche.el`.

A code change updates `arche-diary.el`, the tests and this file in one commit, and user-visible behaviour also updates `README.md`; every defcustom has a README entry. In this file, record non-obvious contracts and their reasons, not a walk through the functions.

Commit subjects are imperative with no type prefix (`Make no-arg HTML export incremental`), under 70 characters; bodies are prose explaining why, wrapped at about 72.

Tests that compare mtimes must set them with `set-file-times`: there is no clock mocking, and two writes in the same tick get equal mtimes.

`Package-Requires` says Emacs 28.1, but there is no CI and a local compile on a newer Emacs won't flag newer APIs, so check an API's version before using it.
